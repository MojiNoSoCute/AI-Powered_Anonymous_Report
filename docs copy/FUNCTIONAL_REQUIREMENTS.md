# เอกสารข้อกำหนดความต้องการเชิงหน้าที่ (Functional Requirements Specification - FRS)
## ระบบรับแจ้งเบาะแสและจัดการเรื่องร้องเรียนลับ (TrustLine / NPRU Sentinel)
**มหาวิทยาลัยราชภัฏนครปฐม (Nakhon Pathom Rajabhat University)**

---

## 📌 วัตถุประสงค์ของเอกสาร (Purpose)
เอกสารฉบับนี้จัดทำขึ้นเพื่อระบุ **ข้อกำหนดความต้องการเชิงหน้าที่ (Functional Requirements: FR)** ทั้งหมดของระบบ TrustLine อย่างละเอียด ครบถ้วน เพื่อให้ทีมทดสอบระบบ (QA / Software Testers) สามารถนำรหัสข้อกำหนด (Requirement ID), เงื่อนไขตั้งต้น (Pre-conditions), ข้อมูลนำเข้า (Inputs), ผลลัพธ์ที่คาดหวัง (Expected Results) และเกณฑ์การยอมรับ (Acceptance Criteria) ไปใช้ในการออกแบบ **Test Cases / Test Scenarios** สำหรับการทดสอบแบบ Manual Testing และ Automated Testing ได้อย่างครอบคลุม

---

## 🏗️ โครงสร้างระบบและโมดูลทั้งหมด (System Architecture & Modules)
ระบบแบ่งออกเป็น 7 โมดูลหลัก ดังนี้:
1. **Module 1: การส่งรายงานเบาะแสลับ (Anonymous Report Submission - FR-SUB)**
2. **Module 2: ระบบวิเคราะห์อัจฉริยะด้วย AI (AI Smart Assistant Analysis - FR-AI)**
3. **Module 3: ระบบติดตามสถานะและการสนทนาลับ 2 ทาง (Status Tracking & 2-Way Encrypted Chat - FR-TRK)**
4. **Module 4: ระบบจัดการสำนวนคดีสำหรับเจ้าหน้าที่ (Case Management Dashboard - FR-CAS)**
5. **Module 5: ระบบแดชบอร์ดสถิติและการวิเคราะห์ (Analytics Dashboard - FR-ANA)**
6. **Module 6: ระบบการยืนยันตัวตนและความปลอดภัย (Authentication & Security - FR-SEC)**
7. **Module 7: ระบบโครงสร้างพื้นฐานและการสื่อสารแบบเรียลไทม์ (System Infrastructure & Real-Time - FR-SYS)**

### Module 1: การส่งรายงานเบาะแสลับ (Anonymous Report Submission - FR-SUB)

| Requirement ID | รายการฟังก์ชัน | คำอธิบายการทำงาน (Description) | ข้อมูลนำเข้า (Inputs) | ผลลัพธ์ที่คาดหวัง (Expected Result) | เกณฑ์การยอมรับ (Acceptance Criteria) |
|---|---|---|---|---|---|
| **FR-SUB-001** | ลำดับขั้นตอนแบบฟอร์ม (Form Step Hierarchy) | หน้าแบบฟอร์มต้องแสดงลำดับขั้นตอนที่ถูกต้องตาม UX Flow | การเข้าสู่หน้าแรก (Submit Tab) | แสดง 4 ขั้นตอนเรียงลำดับ:<br>1. รายละเอียดเหตุการณ์<br>2. เอกสาร/หลักฐานประกอบ<br>3. หมวดหมู่เรื่องร้องเรียน<br>4. ระดับความเร่งด่วน | ลำดับขั้นตอนต้องไม่สลับที่กัน และมีตัวเลขกำกับ 1, 2, 3, 4 ชัดเจน |
| **FR-SUB-002** | การกรอกวันที่เกิดเหตุ | ผู้ใช้สามารถเลือกวันที่เกิดเหตุการณ์ได้ | วันที่ (Date picker) | ค่าเริ่มต้นเป็นวันปัจจุบัน (YYYY-MM-DD) สามารถเลือกวันย้อนหลังได้ | รองรับ Format วันที่สากลและไม่ error เมื่อเลือกวันใดๆ |
| **FR-SUB-003** | การระบุสถานที่เกิดเหตุ | ผู้ใช้สามารถกรอกสถานที่เกิดเหตุภายในมหาวิทยาลัยหรือออนไลน์ | ข้อความสถานที่ (String, max 200 ตัวอักษร) | บันทึกข้อความสถานที่ หากไม่ระบุให้บันทึกเป็น "ไม่ระบุ" | รองรับภาษาไทยและภาษาอังกฤษ |
| **FR-SUB-004** | การกรอกรายละเอียดเหตุการณ์ | ผู้ใช้ต้องกรอกเนื้อหารายละเอียดเหตุการณ์ | ข้อความคำอธิบาย (String, สูงสุด 5,000 ตัวอักษร) | มีเคาน์เตอร์นับจำนวนตัวอักษรแบบเรียลไทม์ (เช่น `150 / 5000`) | หากไม่กรอกคำอธิบายแล้วกดส่ง ระบบต้องแจ้งเตือนและไม่อนุญาตให้ส่ง |
| **FR-SUB-005** | การแนบไฟล์หลักฐาน (Upload & Drag-Drop) | รองรับการอัปโหลดไฟล์หลักฐานทั้งการคลิกเลือกไฟล์และ Drag & Drop | ไฟล์ภาพ (PNG, JPG), เอกสาร (PDF), วิดีโอ (MP4) ขนาดรวมไม่เกิน 50MB | แสดงรายการไฟล์ที่แนบ พร้อมชื่อไฟล์, ขนาดไฟล์, ไอคอนประเภทไฟล์ | แสดงผลจำนวนไฟล์ที่แนบไว้แบบเรียลไทม์ |
| **FR-SUB-006** | การลบไฟล์หลักฐานที่แนบ | ผู้ใช้สามารถลบไฟล์ที่แนบออกได้ก่อนกดส่งรายงาน | คลิกไอคอนถังขยะบนรายการไฟล์ | ไฟล์ถูกลบออกจากรายการแนบ และจำนวนนับลดลงทันที | ไฟล์ที่ถูกลบต้องไม่ถูกส่งไปยังฐานข้อมูล |
| **FR-SUB-007** | ค่าเริ่มต้นของหมวดหมู่ (Category Initial State) | เมื่อเปิดฟอร์มขึ้นมาครั้งแรก ต้องยังไม่มีหมวดหมู่ใดถูกเลือก | เปิดหน้าแบบฟอร์มใหม่ | หมวดหมู่ทั้ง 7 รายการอยู่ในสถานะว่าง (`null`) ไม่มีการติ๊กเลือก แสดงป้าย "ยังไม่ได้เลือก (รอ AI วิเคราะห์)" | ไม่มี Card หรือ Radio button ใดแสดงสถานะ Checked ล่วงหน้า |
| **FR-SUB-008** | การล็อคสิทธิ์การเลือกหมวดหมู่ (Category Access Control) | ผู้แจ้งทั่วไปไม่สามารถคลิกเลือกหรือเปลี่ยนหมวดหมู่ได้เองตามอำเภอใจ | คลิกที่ Card หมวดหมู่ (ขณะเป็นบุคคลทั่วไป) | แสดงเมาส์แบบ `cursor-not-allowed` การคลิกไม่มีผลเปลี่ยนค่า แสดงป้ายเตือน "🔒 เฉพาะ AI และ เจ้าหน้าที่เท่านั้นที่แก้ไขได้" | ผู้ใช้ทั่วไปไม่สามารถเลือกหรือแก้ไขหมวดหมู่เองได้ |
| **FR-SUB-009** | สิทธิ์เจ้าหน้าที่ในการเลือกหมวดหมู่ | หากผู้ใช้เข้าสู่ระบบด้วยสิทธิ์ Admin/เจ้าหน้าที่ จะสามารถคลิกเลือกหมวดหมู่ในแบบฟอร์มได้ | คลิกเลือก Card หมวดหมู่ (ขณะมี Session เจ้าหน้าที่) | หมวดหมู่ถูกเลือกตามที่เจ้าหน้าที่คลิก แสดงป้าย "สิทธิ์เจ้าหน้าที่: คุณสามารถคลิกเลือกปรับเปลี่ยนหมวดหมู่ได้" | เจ้าหน้าที่สามารถเลือกและสลับหมวดหมู่ได้อิสระ |
| **FR-SUB-010** | ค่าเริ่มต้นของความเร่งด่วน (Urgency Initial State) | เมื่อเปิดฟอร์มขึ้นมาครั้งแรก ต้องยังไม่มีระดับความเร่งด่วนใดถูกเลือก | เปิดหน้าแบบฟอร์มใหม่ | ระดับความเร่งด่วนอยู่ในสถานะว่าง (`null`) ไม่มีการติ๊กเลือก แสดงป้าย "ยังไม่ได้เลือก (รอ AI วิเคราะห์)" | ไม่มี Card ระดับความเร่งด่วนใดแสดงสถานะ Active ล่วงหน้า |
| **FR-SUB-011** | การล็อคสิทธิ์ระดับความเร่งด่วน (Urgency Access Control) | ผู้แจ้งทั่วไปไม่สามารถคลิกเปลี่ยนระดับความเร่งด่วนได้เอง | คลิกที่ Card ความเร่งด่วน (ขณะเป็นบุคคลทั่วไป) | แสดงเมาส์แบบ `cursor-not-allowed` การคลิกไม่มีผลเปลี่ยนค่า แสดงป้ายเตือน "🔒 เฉพาะ AI และ เจ้าหน้าที่เท่านั้นที่แก้ไขได้" | ป้องกันผู้แจ้งตั้งระดับวิกฤตโดยไม่มีเหตุผล |
| **FR-SUB-012** | การสร้างรหัสรายงานและ PIN (Credentials Generation) | เมื่อส่งรายงาน ระบบต้องสร้าง Report ID และ PIN อัตโนมัติ | กดปุ่ม "ยืนยันส่งรายงานลับ" | สร้าง Report ID รูปแบบ `TL-XXXX-XXXX` และ PIN 4 หลักสุ่มอัตโนมัติ (1000 - 9999) | รหัส Report ID ต้องไม่ซ้ำกันในระบบ และ PIN ต้องไม่เปิดเผยสู่สาธารณะ |
| **FR-SUB-013** | หน้าต่างแจ้งเตือนสำเร็จ (Success Modal) | แสดงรหัส Report ID และ PIN พร้อมปุ่มคัดลอก | ส่งรายงานสำเร็จ | Popup Modal แสดง Report ID, PIN ชัดเจน พร้อมปุ่ม "คัดลอกรหัสและ PIN" และปุ่ม "ไปหน้าติดตามสถานะ" | เมื่อกดคัดลอก ระบบคัดลอกข้อความลง Clipboard และเปลี่ยนสถานะปุ่มเป็น "คัดลอกแล้ว" |
| **FR-SUB-014** | ปุ่มบันทึกร่างข้อมูล (Save Draft) | ผู้ใช้สามารถกดปุ่มบันทึกร่างข้อมูลในเบราว์เซอร์ได้ | คลิกปุ่ม "บันทึกร่าง" | แสดงข้อความแจ้งเตือนบันทึกร่างข้อมูลเรียบร้อยแล้ว | ข้อมูลไม่สูญหายเมื่อกดปุ่ม |

### Module 2: ระบบวิเคราะห์อัจฉริยะด้วย AI (AI Smart Assistant Analysis - FR-AI)

| Requirement ID | รายการฟังก์ชัน | คำอธิบายการทำงาน (Description) | ข้อมูลนำเข้า (Inputs) | ผลลัพธ์ที่คาดหวัง (Expected Result) | เกณฑ์การยอมรับ (Acceptance Criteria) |
|---|---|---|---|---|---|
| **FR-AI-001** | วิเคราะห์อัตโนมัติขณะพิมพ์ (Auto AI Analysis Debounced) | เมื่อผู้ใช้พิมพ์รายละเอียดเหตุการณ์ถึงเกณฑ์ ระบบจะส่งให้ AI วิเคราะห์อัตโนมัติ | ข้อความคำอธิบายเหตุการณ์ความยาวตั้งแต่ 8 ตัวอักษรขึ้นไป | เมื่อหยุดพิมพ์เป็นเวลา 1,000ms (Debounce) ระบบ AI จะประมวลผลหมวดหมู่และระดับความเร่งด่วนให้อัตโนมัติ | มีการหน่วงเวลา 1 วินาทีเพื่อไม่ให้ยิง API ถี่เกินไป |
| **FR-AI-002** | ปุ่มวิเคราะห์ด้วยตนเอง (Manual Trigger) | ผู้ใช้สามารถกดปุ่มวิเคราะห์ด้วย AI ได้ทันทีโดยไม่ต้องรอดีเลย์ | คลิกปุ่ม "วิเคราะห์ด้วย AI ทันที" | แสดงสถานะ Loading (Spinner) หมุน และเลือกผลลัพธ์ให้ทันทีหลังประมวลผลเสร็จ | ป้องกันการกดซ้ำขณะกำลังวิเคราะห์ (Disabled state) |
| **FR-AI-003** | การจัดหมวดหมู่อัตโนมัติ (Automated Classification) | AI ต้องวิเคราะห์และจับคู่เข้ากับ 1 ใน 7 หมวดหมู่ที่ถูกต้อง | ข้อความรายละเอียดเหตุการณ์และสถานที่ | ระบบเลือกหมวดหมู่ที่ตรงที่สุด พร้อมแสดง Badge "AI เลือกให้อัตโนมัติ" บน Card นั้นๆ | 7 หมวดหมู่รองรับ: Harassment, Compliance, Teaching, Technical, Fraud, Safety, Academic |
| **FR-AI-004** | การประเมินระดับความเร่งด่วน (Urgency Assessment) | AI ต้องประเมินระดับความเร่งด่วนจากระดับความรุนแรงของข้อความ | ข้อความที่มีคีย์เวิร์ดวิกฤต เช่น อาวุธ, ไฟไหม้, ทำร้ายร่างกาย, ยักยอกเงินล้าน | ประเมินเป็น 4 ระดับ: ปกติ (Low), ปานกลาง (Medium), สูง (High), วิกฤต (Critical) หากข้อความทั่วไปให้ default ที่ ปกติ (Low) | ข้อความทั่วไปไม่ถูกดันขึ้นเป็น Critical โดยไร้เหตุผล |
| **FR-AI-005** | การคืนค่าเมื่อลบข้อความ (Auto-Reset on Clear) | เมื่อลบข้อความคำอธิบายจนหมด ระบบต้องรีเซ็ตค่ากลับเป็นว่าง | ลบข้อความในช่องคำอธิบายเหตุการณ์จนว่างเปล่า (`length === 0`) | หมวดหมู่และความเร่งด่วนถูกรีเซ็ตกลับเป็น `null` (ยังไม่ได้เลือก) ทันที | ไม่คงค้างการเลือกของข้อความเก่าที่ถูกลบไปแล้ว |
| **FR-AI-006** | ตัวอย่างทดสอบ AI สำเร็จรูป (Sample Presets) | มีปุ่มทดสอบข้อความสถานการณ์จำลอง 4 หมวดหมู่ยอดนิยม | คลิกปุ่มตัวอย่าง เช่น "💰 ทุจริตงบประมาณ", "🚨 ถูกคุกคาม", "⚡ ไฟฟ้าลัดวงจร", "📚 ทุจริตสอบ" | นำข้อความและสถานที่ตัวอย่างใส่ในฟอร์ม และสั่ง AI วิเคราะห์หมวดหมู่และความเร่งด่วนให้ทันที | หมวดหมู่และระดับความเร่งด่วนเปลี่ยนตามเนื้อหาตัวอย่างถูกต้อง |
| **FR-AI-007** | ระบบสำรองกรณีออฟไลน์ (Offline Rule-Based Fallback) | กรณีเชื่อมต่อ Gemini API ภายนอกไม่ได้ ระบบต้องใช้ Fallback Keyword Engine ภายในได้ | ข้อความภาษาไทย | ระบบยังคงวิเคราะห์หมวดหมู่และความเร่งด่วนได้ ไม่เกิด Error จอขาว | ระบบไม่พังแม้ไม่มีอินเทอร์เน็ตภายนอก |

### Module 3: ระบบติดตามสถานะและการสนทนาลับ 2 ทาง (Status Tracking & 2-Way Encrypted Chat - FR-TRK)

| Requirement ID | รายการฟังก์ชัน | คำอธิบายการทำงาน (Description) | ข้อมูลนำเข้า (Inputs) | ผลลัพธ์ที่คาดหวัง (Expected Result) | เกณฑ์การยอมรับ (Acceptance Criteria) |
|---|---|---|---|---|---|
| **FR-TRK-001** | การค้นหารายงานด้วย Report ID และ PIN | ตรวจสอบสิทธิ์การเข้าถึงรายงานด้วยรหัสคู่ | Report ID และ PIN 4 หลัก | หากถูกต้อง: แสดงข้อมูลคดี, ประวัติไทม์ไลน์ และห้องแชท<br>หากผิดพลาด: แสดงข้อความแจ้งเตือน "ไม่พบรหัสรายงานหรือรหัส PIN ไม่ถูกต้อง" | ป้องกันการสุ่มดูข้อมูลคดีของผู้อื่นโดยไม่มี PIN |

| **FR-SYS-001** | การเชื่อมต่อ WebSocket สองทาง (Bi-directional WebSocket) | อัปเดตข้อมูลข้อความแชทและสถานะคดีทันทีโดยไม่ต้องรีเฟรชหน้าเว็บ | การส่งข้อความ, การเปลี่ยนสถานะ, การลบคดี | ส่งกระจายสัญญาณ (Broadcast / Room Subscribe) ไปยัง Client ที่กำลังเปิดเคสนั้นๆ อยู่ทันที | หน้าจอของเจ้าหน้าที่และผู้แจ้งอัปเดตแบบเรียลไทม์ |
| **FR-SYS-002** | การทำงานร่วมกับ SQLite Database | จัดเก็บข้อมูลรายงาน, ข้อความแชท, ไฟล์หลักฐาน และ Audit Logs | การเรียกคำสั่ง CRUD ผ่าน API/Service | ข้อมูลถูกบันทึกลง SQLite อย่างถูกต้อง ปลอดภัย และไม่สูญหาย | รองรับทั้งการรันผ่าน Node.js Full-Stack และ Python Flask Backend |
| **FR-SYS-003** | การกำหนด Port ผ่าน Environment Variable | รองรับการกำหนด Port ของแอปพลิเคชันจาก Environment | ค่า `PORT` ใน Environment Variable หรือ `.env` | เซิร์ฟเวอร์อ่านค่า `process.env.PORT` หรือ fallback เป็น `3000` และพิมพ์ Log ระบุ Port ชัดเจน | ใช้งานบน Docker และ Cloud Environment ได้อย่างยืดหยุ่น |
| **FR-SYS-004** | การรองรับ Docker & Docker Compose | สามารถ Containerize และสั่งรันแอปพลิเคชันผ่าน Docker ได้ | `docker-compose up --build` | สร้าง Image, ติดตั้ง Dependencies, รันแอปพลิเคชันบน Port ที่กำหนดได้อย่างสมบูรณ์ | รันได้ด้วยคำสั่งเดียวโดยไม่ต้องติดตั้งเครื่องมือเสริมในเครื่องโฮสต์ |

## 🎯 แนวทางการนำไปสร้าง Test Cases (Test Design Guidelines for QA)

สำหรับการแปลงข้อกำหนดข้างต้นไปเป็นชุดการทดสอบ แนะนำให้แบ่งประเภทการทดสอบดังนี้:

1. **Functional Positive Testing**:
   - ทดสอบ Flow ปกติตั้งแต่กรอกฟอร์ม -> AI เลือกหมวดหมู่และความเร่งด่วน -> รับ Report ID และ PIN -> นำไปติดตามสถานะ -> สนทนาแชทกับเจ้าหน้าที่
2. **Access Control & Security Testing**:
   - ทดสอบความพยายามคลิกเลือกหมวดหมู่และความเร่งด่วนด้วยบทบาทบุคคลทั่วไป (ต้องถูกล็อค)
   - ทดสอบการเข้าถึงหน้า Case Manager โดยไม่มี Session เจ้าหน้าที่ (ต้องถูกปฏิเสธ)
   - ทดสอบการกรอก PIN ผิดในหน้าติดตามสถานะ (ต้องไม่แสดงข้อมูลคดี)
3. **AI Integration & Edge Case Testing**:
   - ทดสอบพิมพ์ข้อความสั้นกว่า 8 ตัวอักษร (AI ต้องยังไม่ทำงาน)
   - ทดสอบพิมพ์ข้อความภาษาไทยหลากหลายหมวดหมู่ (ตรวจสอบความแม่นยำในการเลือกหมวด)
   - ทดสอบลบข้อความทั้งหมดออก (สถานะหมวดหมู่และความเร่งด่วนต้องรีเซ็ตกลับเป็นว่าง/null)
4. **Real-Time & Boundary Testing**:
   - ทดสอบเปิด 2 หน้าต่างพร้อมกัน (หน้าต่างผู้แจ้ง และหน้าต่างเจ้าหน้าที่) แล้วส่งข้อความแชทเพื่อตรวจสอบความเร็วในการแสดงผลและการนับข้อความที่ยังไม่อ่าน
   - ทดสอบอัปโหลดไฟล์หลักฐานขนาดเกิน 50MB หรือไฟล์ผิดประเภท
   - ทดสอบการส่งออกไฟล์ CSV และตรวจสอบภาษาไทยใน Excel (ต้องไม่เป็นตัวอักษรต่างดาว)
